## 4. Reachable-but-unguarded routes under role-gated sections

| Route | Issue |
|---|---|
| `/dashboard/admin/**` | `middleware.ts` excludes `/dashboard/admin` from all three role redirects (lines 71–78 only check `!startsWith('/dashboard/trainer')`, `!startsWith('/dashboard/athlete')`, `!startsWith('/dashboard/admin')`, `role !== 'parent'`). Middleware itself never verifies an admin role for this prefix — any authenticated user with role `parent`, `trainer`, or `athlete` passes the middleware layer for `/dashboard/admin/*`. The actual admin check lives only in `app/dashboard/admin/layout.tsx` (queries `admin_roles`, redirects to `/dashboard` if absent), so the route ends up correctly protected, but by the page-level layout, not by the same middleware mechanism that gates every sibling role section. |
| `/onboarding/parent`, `/onboarding/setup`, `/onboarding/trainer` | Not in `middleware.ts` `gatedPrefixes`. Auth is enforced only by a client-side `router.replace('/login')` inside each page's `useEffect`/handler — the initial server-rendered HTML and any data-fetch that races the redirect is not blocked server-side the way `/dashboard/**` is. |
| `/child/[id]`, `/child/create` | Not in `gatedPrefixes` and no in-page auth check at all — fully reachable by anonymous users despite living under what is otherwise a parent-only data model. (`/child/[id]` currently only renders mock data, so no live data is actually exposed today.) |
| `/review`, `/booking`, `/notifications` | Not in `gatedPrefixes`; each does a client-side `getUser()` but only degrades gracefully (error message / empty state) instead of redirecting — pages are fully reachable unauthenticated. |
